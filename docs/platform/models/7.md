# Phase 7 — Course Structure (Modules, Lessons & Content)

This is where your platform becomes an actual **Learning Management System (LMS)**.

Instead of uploading random videos, institutions create a structured learning path.

```
Institution
    ↓
Course
    ↓
Modules (Sections)
    ↓
Lessons
    ↓
Content
(Video, PDF, Quiz, Assignment, Live, External Link)
```

This phase should **only** manage the structure and content organization. Student progress, quizzes, and assignments are handled in later phases.

---

# Goal

Allow instructors to:

* Create modules
* Reorder modules
* Create lessons
* Attach videos/PDFs
* Set lesson visibility
* Lock lessons
* Schedule publishing

# Validation Rules

### Module

* Title required
* Minimum 3 characters
* Maximum 100 characters

### Lesson

* Title required
* Lesson type required
* Every lesson must have one content source

### Content

* Video → file_id required
* PDF → file_id required
* Link → external_url required
* Text → text_content required

### Publishing

Cannot publish a lesson unless:

* Title exists
* Content attached
* Module exists
* Course is not archived

# Business Rules

* Every module belongs to exactly one course.
* Every lesson belongs to exactly one module.
* Every lesson must have one primary content source (video, PDF, link, or text).
* Resources are optional supporting materials.
* Lesson order and module order are controlled independently using `position`.
* Preview lessons can be watched without enrollment (subject to course visibility).
* Publishing a lesson requires valid content and an active course.
* All uploaded files reference the **Storage Service** via `file_id`; lessons never store file paths directly.
* Scheduled lessons automatically transition from `SCHEDULED` to `PUBLISHED` when their publish time is reached (implemented by a background scheduler in a later phase).

## Architecture Improvement

For long-term scalability, I recommend one refinement over the earlier phases:

Instead of separate endpoints like:

* `/lessons/{id}/publish`
* `/lessons/{id}/draft`
* `/lessons/{id}/schedule`

use a single state-transition endpoint:

```http
PATCH /lessons/{lesson_id}/status
```

with a request such as:

```json
{
  "status": "PUBLISHED"
}
```

or

```json
{
  "status": "SCHEDULED",
  "publish_at": "2026-08-15T10:00:00Z"
}
```

This approach scales better as more lesson states are introduced and keeps the API more consistent.
